# Phase 2 — Sprint 4a: Allow Duplicate Departments in Exam Package

- **Phase:** 2 — Examination Core
- **Sprint:** 4a (patch to S4)
- **Priority:** 🔴 Critical
- **Django App(s):** `examinations`, `accounts`
- **Depends on:** Sprint 4 (dynamic form), Sprint 5 (examination entry), Sprint 6 (Excel import), Sprint 6a (pricing), Sprint SF1 (frontend)

---

## Goal

Remove the `unique(ExamPackage, Department)` constraint so the same department can appear in an exam package with multiple different templates. Example: Department "Xét nghiệm" with template "Xét nghiệm máu" AND template "Xét nghiệm nước tiểu" in the same package.

---

## Background

Current constraint `unique_department_per_package` treats **Department** as the atomic unit in an ExamPackage. But in practice, one organizational department (e.g., "Xét nghiệm") may have multiple distinct exam activities (blood test, urine test) represented by different `DepartmentTemplate` instances. The atomic unit should be `(Department, Template)`, not `Department` alone.

## Technical Notes

- **Pricing behavior is intentional:** when department "Xét nghiệm" appears 3 times with different templates, `total_cost` sums fields from all 3 templates. This is correct because each template represents a distinct exam procedure with its own costs.
- **`template_snapshot` dedup in spawn:** `template.fields_config` is a JSON list — must convert to hashable form (e.g., `json.dumps(..., sort_keys=True)`) for set membership.
- **Frontend key strategy:** Switch from semantic keys (`department.id`) to synthetic keys (`ExamPackageDepartment.id` / `DepartmentResult.id`) throughout. These are always unique per row.
