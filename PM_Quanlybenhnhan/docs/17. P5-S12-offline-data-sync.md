## Goal

Deliver true offline-first data capability: mirror server data in IndexedDB, queue local changes while offline, and sync bidirectionally with per-field conflict resolution when connectivity returns.

## Sync Protocol

### Pull
```
GET /api/sync/pull?since=<ISO_timestamp>&client_id=<uuid>
```
```json
{
  "updated": [
    {"model": "Examination", "id": 1, "data": {}, "version": 5, "updated_at": "..."}
  ],
  "deleted": [ {"model": "Examination", "id": 2} ],
  "server_time": "2026-07-01T12:00:00Z"
}
```

### Push
```
POST /api/sync/push
```
```json
{
  "client_id": "uuid",
  "changes": [
    {"model": "Examination", "id": null, "data": {}, "version": 0, "operation": "create"},
    {"model": "Examination", "id": 5, "data": {}, "version": 3, "operation": "update"}
  ]
}
```

---

## Conflict Resolution

1. Client pushes a change with the `version` it last saw.
2. If server `version` > client `version` → conflict.
3. Attempt per-field merge (keep latest modified field values).
4. Unresolvable fields → last-write-wins, and log a `SyncLog` entry with `status='conflict'`.
5. Admin reviews conflicts in the Sync status UI.

## Acceptance Criteria

- With network off, a user can create/edit examinations; changes persist in IndexedDB
- On reconnect, queued changes push to the server and receive server IDs/versions
- Concurrent edits produce a documented, deterministic resolution (per-field merge / LWW)
- Conflicts are recorded and visible to Admin
- First-visit initial load populates IndexedDB with required reference data
- Sync status UI shows last-synced, pending, and conflict counts

---

## Technical Notes

- All syncable models expose `version` (from `VersionedModel`) and `updated_at`.
- Use client-generated UUIDs for offline-created records to avoid ID collisions, mapped to server IDs on push.
- Background Sync API retries pushes; fall back to on-online event for unsupported browsers.
- Sync is Admin/Doctor/Nurse/LabTech only (CompanyAdmin/Patient excluded per matrix).
